# ADR-0041: Database functional qualification and bounded runner I/O

- Status: Proposed
- Date: 2026-11-26
- Authors: Coglet contributors
- Related PR: to be assigned
- Supersedes / superseded by: none; extends the infrastructure/semantic-time distinction of ADR-0021 only for the fixed-input database engine-seam adapter

## Context

PR187 exact `084d129ce95536952f4519581d6646baaa8097f6` failed the real
`db-paging-cursor` exchange in Rust run45818889246/job139905816300:
`AssertionError: step 1: TimeoutError`. Seven other database cases passed.
This establishes an exceeded wall-clock response window, not which syscall or
scheduler interval stalled. The same source passes the original complete real
corpus locally; no production database or cursor defect follows from that fact.

The database corpus generated by `spec/tests/build_database.py` assigns 500ms to
functional response reads. The engine-seam example provisions disposable SQLite
state, compiles request guest bytes, durably commits a real cursor-seeding guest
step when needed, then executes the requested real/mock guest and recovery path.
These synchronous operations run inside that wall-clock window. The underlying
[database contract](../../spec/capabilities/database.md) requires isolation, bounded queries,
authority, atomicity, durable recovery and replay; it does not promise a 500ms
end-to-end result from a loaded CI worker.

Unlike the surface peers in ADR-0021, this adapter already fixes ABI input logical
time to10 and seed to7 independently of runner time. The frozen database cases
contain no protocol-time schedules, silence intervals or live expiry checks.
Its actual engine wall-time, compute, memory and host-byte budgets remain active.
A surface clock-control channel is neither present nor needed for this adapter.

A discarded readiness-only experiment moved fixed fixture provisioning/seed work
before readiness and retained full actual request execution afterward. It passed
initially, but under later host load it still produced post-readiness 500ms
response timeouts, and startup could exceed5s. Therefore startup separation alone
is not an adequate correction. The exact historical CI stall remains unknown.

## Decision

Introduce an explicit test-only registry boolean
`database_functional_watchdog = true`, admitted only for stdio implementations
whose sole suite is `database`, whose sole peer role is `guest`, and which do not
opt into surface fixture clocks or schedulers. Unknown fields, nonboolean values,
other suites/roles/transports and mixed clock bindings fail configuration before
any peer is launched.

For opted-in functional database exchanges, use a fixed **5000ms runner I/O
watchdog** for sending and receiving a complete frame. Keep the existing bounded
startup and whole-case watchdogs (currently5000ms and10000ms by default), process
group termination/reaping, maximum frame lengths, EOF/partial-frame refusal and
exact byte/value comparisons. No retry, skip, fabricated result or unbounded
wait is introduced. A missing/hung responder still fails within these bounds.
Non-opted-in implementations retain existing `within_ms` behavior.

The binding is eligible only for functional request/response cases. Before launch,
reject opted-in cases carrying `at_ms`, `silence_ms`, `expect_close`, stream/finish
controls or any other protocol-time/transport scheduling assertion. Existing
case validation and every ordinary response/journal assertion still apply. This
is not a generic escape hatch for slower surface, hub, engine or product tests.

Use a crate-owned generated registry for the real and mock database adapters in
`crates/coglet-runtime/tools/check-database.py`. The frozen corpus, message
schemas, production daemon, database implementation, WAMR engine, real durable
store and request-time guest work remain unchanged. The adapter must continue to
supply the fixed logical-time/seed inputs and authenticate the actual request's
grants, code, catalog and schema through the ordinary runtime path. It must not
read expected replies or case names to determine results.

No product wire/schema or production timing requirement changes. The sole
conformance configuration change is the narrowly qualified registry binding and
its interpretation of functional runner I/O. This decision must land docs-only
through independent review, exact-head CI and the normal merge queue **before**
its implementation is published.

## Alternatives

- Retry required CI until green or quarantine the functional case: rejected as
  the delivery correction. It does not repair the exposed timing boundary.
- Increase frozen `within_ms` globally: rejected; changes every consumer's timing
  interpretation and can hide real protocol-time assertions.
- Set `fixture_clock` on a database peer without implementing its surface control
  channel: rejected; a false clock claim must not qualify.
- Startup/readiness preparation alone: insufficient; the preserved experiment
  still fails during actual durable request execution under load.
- Remove durability or return cached/canned expected replies: rejected; invalidates
  real/mock same-suite qualification and recovery guarantees.
- Disable production engine wall-time budgets: rejected; runner I/O tolerance is
  not authority to change guest execution limits.

## Consequences

Functional database passes establish exact real/mock semantics and durability,
not live service latency or a universal scheduling bound. Preserve any actual
production deadline failure as a failure; no clock adjustment follows from this
binding. Existing live-time safety and device-lifecycle tests remain separate
required gates. A runner stall beyond the finite watchdog still fails closed.

The change touches shared harness configuration/validation and therefore requires
coordination with its owner and independent exact-head review. It does not
expand PR187's producer APIs or move M3 policy/promotion/rollback into cogletd.
The failing original run and unsuccessful readiness experiment remain evidence,
not qualified results or a reason to waive hosted acceptance.

## Verification

Before implementation, obtain independent review and land this docs-only ADR.
Then require all of the following on the implementation head:

- Registry admission negatives for nonboolean values, wrong/mixed suite,
  wrong/mixed role, non-stdio transport and conflicting clock/scheduler bindings.
- Case-preflight negatives for timed/silence/closure/stream assertions, plus
  non-opted-in behavior unchanged. Invalid admission must launch no peer.
- A deterministic setup/request delay greater than500ms but less than5000ms:
  the original direct invocation fails, and the opted-in actual database adapter
  passes the identical frozen paging request with real WAMR and real SQLite/WAL
  work. Record full source/command/exit evidence; do not label an injected stall
  as the historical syscall cause.
- Full unchanged database corpus on both real and mock adapters, with fresh
  exact JUnit names/counts and zero failed/skipped cases. No expected response is
  passed to an implementation.
- Hung/missing responder, partial-frame/EOF, oversized frame and wrong-response
  controls still fail; startup/whole-case bounds and process teardown remain
  effective. Transport fakes prove watchdog behavior only, not DB semantics.
- Actual request authority, cursor continuation, abort, marker-absent recovery,
  marker-present recovery and replay tests remain required. Source review verifies
  fixed logical-time/seed binding and unchanged production guest budgets.
- Independent exact-head implementation review, every required exact-head CI
  context green, then normal head-pinned queue landing. The original PR187
  producer acceptance and actual MERGED requirement are not waived.

## Approval

Proposed; neither this document nor local experiments authorize implementation
publication before the docs-only PR is reviewed and actually merged.
