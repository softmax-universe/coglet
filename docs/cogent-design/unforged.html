Coglets on unforged#

How coglets are stored, stepped, patched and shipped if the cogent's storage and execution layer is unforged: a coglet is a git ref, a step is a commit, a patch is a merge, and the router is an unforged repository. Part of the cogent design.

Status: proposed. Nothing here is frozen. Adoption is staged: only the state-hash change is planned now; see Coglets and unforged: staged integration. Where this page and the specs disagree, this page describes the intended change; the spec changes section lists what each spec would need.

The idea#

Today a coglet's state is a flat map of files hashed as one CBOR value, its journal is a separate trace format, and code reaches a device as a git bundle. Three formats describe one thing. This design keeps one: git objects with SHA-256 ids, the format unforged is already built on.

Coglet concept Becomes
A coglet A ref, refs/coglets/<id>/state
Its memory, code and logs The tree of the commit that ref points at
One step One commit, with the previous state and the step's input as parents
The state hash The git tree id of that commit
The journal The ref's history
A patch A commit on …/policy, merged into the state between steps
Promotion A signed compare-and-swap of refs/published/<id>
The router's store An unforged repository holding every coglet's refs

What does not change: adapters, events and actions, handle(), all-or-nothing steps, grants, and the rule that nothing leaves a runtime until a step has committed. Coglets do not see any of this; their code still reads and writes /data and returns.

Three places, one object format. Devices step coglets in process. The router is an unforged daemon. The centre steps its own coglets the same way and can send any step to unforged workers on CAOS.

Two speeds. unforged as it stands runs every program as a separate process and calls the git binary for most operations. That is fine for jobs and far too slow and too heavy for a voice turn on a phone. So the design has two runners that produce the same objects:

  • the hot path, cogletd, which writes git objects in process with no fork and no git binary, on every device;
  • the cold path, unforged's river exec, which runs one step as a cached job, at the centre or on CAOS workers.

The rule that ties them together: for the same state and the same input, both runners produce the same commit id. That is the conformance check.

A coglet is a ref#

The refs of one coglet, its step commits, and the tree of the latest one.

Each coglet has four refs under refs/coglets/<id>/:

Ref Points at Moved by
state The commit of its latest step The runtime, once per step
policy Candidate code, prompts and skills Its manager: the factory, the optimizer or a person
published The policy the cogent has promoted The router kernel, after probation
inputs The latest recorded input The runtime, once per step

On the router, each runtime's refs live in their own namespace, refs/namespaces/<node>/refs/coglets/<id>/…, so a device can only ever move its own refs. unforged already gives each process its own GIT_NAMESPACE; here a namespace is a runtime instead of a process.

CogletTree
  The tree of every step commit. Paths are the ABI's paths without the leading slash.
  manifest.cbor        Manifest   What it subscribes to, needs and owns. Host-owned.
  code/bin/step.wasm   bytes      The policy's code. Host-owned.
  code/prompts/…       bytes      Prompts, if the policy has any. Host-owned.
  code/skills/…        bytes      Skills, if the policy has any. Host-owned.
  data/…               bytes      Its memory. The guest writes these.
  data/inbox.jsonl     bytes      Append-only. Only the runtime writes it.
  logs/events.jsonl    bytes      Append-only.
  out/actions/<id>     Action     Effects this step staged. Empty after a failed step.
  out/timers/<id>      Timer
  out/llm/<id>         LlmRequest

Rules for the tree:

  • Every file is a regular file with mode 100644. No symlinks, no gitlinks, no .git* entries, no empty directories. The ABI's path rules already rule these out, so every valid ABI snapshot maps to exactly one tree and back.
  • out/ holds only what this step staged. The next step starts with out/ empty. A dispatcher reads out/ from the commit the state ref points at and records what it sent in refs/notes/dispatched, keyed by commit; that note, not the tree, is the effect ledger.
  • code/ and manifest.cbor change only through a patch, never through a step.

A step is a merge#

unforged's central idea is that running a program is a three-way merge: program ⊕ input → output. A coglet step fits it exactly. The coglet's state is "ours", one input is "theirs", and the resolver names the engine that merges them.

One step. The resolver pins the engine build by id, so the cache key covers which engine ran, not just which coglet.

InputTree
  Everything one step reads besides the coglet's own tree. One commit per step.
  events.cbor       [Event]    The batch, oldest first.
  context.cbor      StepContext
  boundary.cbor     [Change]   Debug writes and inbox appends applied before this step.
  replies/<id>      bytes      Model replies and read results delivered as events, verbatim.

StepContext
  step          u64
  logical_time  u64
  seed          u64
  grants        [OpName]
  budgets       Budgets

StepCommit
  Built so that replaying the same step yields the same commit id.
  tree       TreeId     The coglet's tree after the step.
  parents    [state n, input n]
  author     the coglet id, at logical_time
  committer  the coglet id, at logical_time
  message    "step <n>"
  trailers   Coglet-Step: <n>
             Engine: <resolver commit id>
             Status: committed | aborted

Decisions this makes:

  1. The state hash is the git tree id. It replaces the SHA-256 of the whole snapshot as one CBOR map. A step that changes one file rehashes that file and the trees above it, not every byte the coglet owns. Any git tool can check it.
  2. Step commits are deterministic and unsigned. Author and committer are the coglet at logical time; there is no wall-clock time and no signature in the commit. Replaying a step must reproduce the exact commit id, which is a stronger check than comparing state hashes. Signatures go on ref updates instead (see Signatures).
  3. Observed usage is not in the commit. Compute used, wall time and memory high-water go in refs/notes/usage, because wall time differs between runs.
  4. A failed step still makes a commit. Its tree is the previous tree with out/ empty, and its trailer says Status: aborted. The step counter and the inputs it consumed stay in history, as the journal requires today.
  5. The engine is part of the input. The resolver tree pins the engine build (for example coglet-engine-wamr at a given id) and says whether that engine is qualified as deterministic. The cache key is (resolver, state tree, input tree), so changing the engine can never reuse a result from another engine.

Two runners#

Hot path: cogletd Cold path: unforged river exec
Where Every device, and the centre's live coglets The centre and CAOS workers
Process model One process; steps run in it One sandboxed process per step
Git In-process object writer; no git binary unforged, which calls git
Engine WAMR, with compute and deadline metering The same engine build, named by the resolver
Writes Step commits, moved with a local ref compare-and-swap The same commits, plus a cache entry and a receipt
Cache None: every live step runs refs/notes/memoization locally, CAOS's cache remotely
Used for Live work: voice, apps, the fast loop Replays, forks, gates, factory tests, simulations

The hot path. coglet-fs becomes a git-tree store: blobs and trees are written in process as SHA-256 git objects, loose at first and packed in the background. The state ref is updated with a compare-and-swap in a small ref store of its own. Nothing forks, so it works on iOS and the EO1. Commits are cheap: a step that changes one file writes one blob, the trees above it, the input commit and the step commit.

The cold path. A step becomes an unforged job: the program tree holds the engine and a small driver, coglet-step, that runs exactly one step and writes the output tree; the input is the coglet's state merged with one input commit. unforged takes care of sandboxing, caching, provenance trailers and, with a caos:// ticket, running the job on a CAOS worker.

Replays, forks and gates#

The device writes the journal; the centre re-runs it.

Use What runs Passes when
Replay Each recorded step, with the cache turned off Every commit id matches the recorded one
Fork A recorded state with a new input Always; the result is a new branch
Gate A candidate policy over recorded inputs The kernel's promotion checks hold on the new branch

Because every step is keyed by (resolver, state tree, input tree), a thousand forks that share a prefix share the work for that prefix, and two factory tickets that test the same patch on the same inputs run it once.

Each job leaves a receipt, so a cached answer is never mistaken for a fresh run:

StepReceipt
  Kept in refs/notes/receipts, keyed by the step commit.
  runner        "cogletd" | "unforged" | "caos"
  worker_image  str?       The resolved worker image, for CAOS jobs.
  executed      bool       False if a cache supplied the result.
  cache         "none" | "local" | "caos"
  commit        CommitId

Rules:

  • Replay always executes. A replay that a cache answers proves nothing, so replay jobs run with the cache off and their receipts must say executed: true.
  • Only qualified engines are cached. A resolver that is not marked deterministic is never cached and never shared through CAOS.
  • Model calls never run in a replay. Replies are blobs in the input tree; a missing reply fails the step, as today.

Patches are merges#

A patch from the factory to a running coglet. Steps 5 and 6 happen between two of the coglet's steps.

A patch is a commit on refs/coglets/<id>/policy. Its tree changes code/, may change manifest.cbor, and may carry a migration program for data/. Applying it is a merge of the policy into the state, governed by the coglet's resolver:

PatchAttributes
  The resolver's attributes for applying a patch.
  code/**         merge=theirs     The patch's code replaces the old code.
  manifest.cbor   merge=manifest   The new manifest is admitted again against the coglet's grants.
  data/**         merge=migrate    Runs the patch's migration program, if it has one; otherwise keeps data.
  logs/**         merge=ours       Logs are never patched.
  • base is a compare-and-swap. Patch.base is the policy commit the patch was made from. If the ref has moved, the push is refused, as the back channel already specifies.
  • A conflict pauses the coglet. If the migration fails or the new manifest asks for more than is granted, the merge stops with a conflict tree, the coglet is paused, and its manager resolves it through the back channel. This is unforged's PAUSED_CONFLICT with a coglet as the process.
  • The patch is tested the same way it is applied. The factory merges the patch into recorded states and runs the recorded inputs through it as a gate before pushing. That is the "build, test" step in the end-to-end request.

The back channel maps onto git operations:

Back channel Becomes
patch Push to …/policy; the runtime merges it at the next boundary
tail_log Fetch of logs/ from new step commits; live tailing stays a stream
read_state Partial fetch of one path from the state commit, needing a read grant
status The state ref, its last trailer, and health
pause, step Unchanged messages; a paused coglet's ref simply stops moving

The router is an unforged repository#

The router stays what the cogent design says it is: a coglet that finds devices and carries messages and patches. unforged is its storage and its git transport.

  • One repository per cogent. Every coglet's refs, namespaced by runtime. refs/published/<id> and the kernel's probation refs live outside the runtime namespaces, and only the kernel moves them.
  • Install, start and deploy become ref moves. To install a coglet on a device, the router moves the device's published ref; the device fetches it over iroh and starts the coglet from that tree. coglet deploy becomes a signed push to the router. This is the chain the CLI's deploy command is waiting for today.
  • Messages stay on streams. Messages, health, pause and step keep the router protocol's QUIC streams. Only state, code and logs move as git, on a separate ALPN on the same iroh endpoint.
  • Private data stays private. A runtime pushes its state commits with data/ blobs left out, as a partial push; the router holds the trees and ids but not the bytes. Fetching data/ blobs needs the same read grant as read_state, and replays at the centre need it explicitly. This keeps the current rule that /data never leaves a device without a grant.

Signatures#

  • Step commits are not signed (they must replay to the same id). The runtime signs each ref update instead: a statement naming the ref, its old commit and its new commit, as ref-statement does today, with the same Ed25519 node keys. The router keeps those statements in refs/notes/statements.
  • Policies and promotions are signed by whoever moves the ref: the factory or a person for policy, the kernel for published. unforged's allowed_signers holds those keys and which refs each may move.
  • Signatures survive translation. When objects pass through a store with other ids, such as CAOS's SHA-1 store, the original signed commit id is kept in a Source-Commit: trailer and that is what is verified. A translated object never counts as signed by its original author. The better fix is for CAOS to store SHA-256 objects, and this design asks for it.

What it costs#

Cost Mitigation
A few object writes per step on every device Writes are in process, batched to disk, and packed in the background
History grows with every step Compaction: keep recent steps, roll older ones into checkpoints (river compact / gc already exist)
Recorded model replies make inputs large Replies are blobs, shared when identical, and dropped with old inputs
The cold path needs git and process spawning Only at the centre and on workers, never on devices
Two runners can drift Conformance runs every fixture through both and compares commit ids

Spec changes#

Spec Change
spec/conventions.md Object ids are git SHA-256. CBOR stays for message and file contents.
spec/abi.md State hash is the git tree id. The journal and trace become step commits, input commits and notes. Usage moves to a note. A failed step makes a commit with an unchanged tree. Effects are staged under out/.
spec/manifest.schema.json The manifest lives in the tree as manifest.cbor and names its resolver (engine) by id.
spec/hub-protocol.md Git transfer moves from SHA-1 bundles to fetch and push of SHA-256 refs over a git ALPN, with partial push for data/. hub.git.push, install and start become ref moves. Per-coglet repositories become one repository per cogent, namespaced by runtime.
spec/promotion.md, spec/policy.md Promotion is a signed compare-and-swap of refs/published/<id>. Gates are replays on the cold path.
spec/tickets.md A ticket's result names a policy commit and the receipts of the gate that tested it.
spec/surface-protocol.md No change.

unforged would need:

  • an in-process object writer shared with coglet-fs, so the hot path and unforged agree byte for byte;
  • the resolved worker image in its cache key, and receipts that say whether a job ran;
  • the coglet-step driver and a resolver attribute for patch migrations.

Open questions#

  • Commit rate on voice. A fast conversation can step a coglet many times a second. Every step still gets a commit, but the hot path may need group commit to disk; measuring this on the EO1 comes first.
  • Where the inbox lives. data/inbox.jsonl in the tree keeps replay simple but makes the inbox part of every state hash. An alternative is to keep the inbox only in input commits.
  • Migrations. A data/ migration program has to be deterministic and metered like a step. Whether it runs on the coglet's engine or as its own job is open.
  • CAOS and SHA-256. Until CAOS stores SHA-256 objects, cold-path jobs on CAOS rely on unforged's SHA-1 translation, with the signature limits above.

First test#

Run the counter coglet for a few steps with cogletd, then replay each step as an unforged job with the cache off. The commit ids must match. Run the replay again with the cache on: every receipt must say executed: false. Change only the engine pin in the resolver and run again: every receipt must say executed: true.
